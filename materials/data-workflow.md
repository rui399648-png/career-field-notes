# 数据分析 · 工作材料

所有活动、身份、日志、状态和相关方反馈均为虚构教学模拟，不来自真实用户，也没有测量你这次作品的效果。主轮 45 分钟，可用浏览器、纸笔或文本编辑器完成，不要求 Excel、Python、账号、花钱或安装依赖。

职责参考：[Amazon 北京 Business Analyst Intern](https://amazon.jobs/en-gb/jobs/10492602/business-analyst-intern-global-selling-rest-of-asia)正文包含数据收集、指标跟踪、跨团队分析与报告；它是国内地点的外资实习样本，要求高级 Excel 与英语，Python/SQL 为优选，不代表你已经符合应聘条件。[Microsoft PL-300 官方技能指南](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/pl-300)包括业务需求、数据质量、转换/聚合与分析。只借用工作活动，不要求 Power BI 或考证。来源实际全文访问：2026-10-07；不据岗位样本声称国内招聘热度。

## 0–5 分钟：把问题和统计口径说清

组织者初始问题：“A 信息群和 B 分享卡都指向同一活动页。哪种来源的访问→成功提交比例较高？下一次我们该观察什么？”

本轮活动仍是手机摄影入门工作坊，20 名、免费、手机即可、零基础；不执行真实推广或名单管理。此次日志是独立缩小的教学样本，不与其他题的 100 位访客、渠道触达数或报名文件合并。

先写一句：我准备比较哪些人、在什么时间、完成什么行为。初始主要指标是 **成功提交人数 / 可识别访客人数**；辅助指标是 **成功提交人数 / 点击人数**。两者分母不同，不能都笼统叫“转化率”。这里的 submit_success 只证明表单保存成功，不能当作当前正式报名名额。

原始日志是截至模拟 **2026-10-07 18:00** 的固定教学截取，只回答已取得日志中的窗口内行为。统计窗口尚未走完，不能把本次比例当作已结算的完整七天结果；后续窗口内事件尚不在这份材料里。

统计规则：

1. 窗口为模拟上海时间 **2026-10-01 00:00（含）至 2026-10-08 00:00（不含）**。日志时间带 `+08:00`；不要只凭日期看起来接近就纳入。
2. user_id 去两端空格并转为小写。同一身份每一步计一次，事件行数不是人数。ID 规范化是保留行、统一身份，不是直接删除看起来奇怪的行。
3. 只纳入非测试、窗口内、ID 非空的事件。缺失 ID 先隔离，不能用行号或随便编的名字替代；这会让最终分母只代表可识别访客。
4. 相同 event_id 代表重复记录，保留第一条；本题重复记录除了 row_id 都一致。若真实数据出现同 event_id 内容冲突，需调查，不能按本题规则就说已解决。
5. 本题每人渠道由首次有效 visit 固定，后续事件渠道一致，两个渠道人群不重叠。两个来源的分母都是进入同一活动页的人，**不是信息群收信人数与分享卡曝光数**。真实识别、跨设备去重及归因仍需另行验证。

## 5–20 分钟：检查原始日志，计算 V1

打开 [原始日志浏览器表格](data-table.html) 或 [data-events.csv](data-events.csv)。CSV 可在文本编辑器查看；已有表格工具也可使用。不要先打开参考答案。原始日志有 29 行。

| 字段 | 含义 |
| --- | --- |
| row_id | 原始文件行标识，用来引用处理证据。 |
| event_id | 一次记录事件的标识；重复标识应检查。 |
| user_id | 虚构身份；只按本题的空格/大小写规则统一。 |
| channel | A 信息群、B 分享卡的活动页来源标签。 |
| event | visit 访问页；click 点击报名入口；submit_success 表单保存成功。 |
| occurred_at | 带上海时区偏移的模拟发生时间。 |
| is_test | 1 为教学测试记录，0 为非测试记录。 |

先扫一遍重复、空 ID、测试标记及窗外记录。写至少四类质量处理证据；注意规范化后能关联到原身份的行应该保留。每条用 `行号｜问题｜保留/排除/规范化/待确认｜理由`，不要只写“清洗好了”。

保留原文件；在笔记里记录原始行数、排除行及原因、最终纳入事件行数。再为两个来源列出去重 ID 集合：

| 来源 | 访客 ID | 点击 ID | 提交 ID |
| --- | --- | --- | --- |
| A | 自己填写 | 自己填写 | 自己填写 |
| B | 自己填写 | 自己填写 | 自己填写 |

核查：每个点击者都应有 visit；每个提交者都应有 click。若不成立，先检查大小写、空格、时间或缺失记录，不能自动补事件让漏斗成立。这里只计算有足够行为证据的同一批身份。

然后填表。比例可以保留一位小数，分数也可以；**先写分子、分母，再除**：

| 来源 | 可识别访客人数 | 点击人数 | 提交人数 | 提交/访客 | 提交/点击 |
| --- | --- | --- | --- | --- | --- |
| A |  |  |  |  |  |
| B |  |  |  |  |  |
| 合计 |  |  |  |  |  |

保存 V1：一句观察、一个数据局限、下一步希望补什么。样本小、来源受众未控制，没有对照试验，不能说某来源造成更高比例，也不能以比例高直接决定全部转移。缺 ID 被隔离后，分母不等于所有真实访客。

## 20–35 分钟：新业务问题与计算 V2

组织者：“你的成功提交比例回答了第一个问题。现在排预备名单，我要知道当前有效报名。请对照状态快照补一个指标；原来的提交指标也保留。B 的比例较高，能决定下一次全部转到 B 吗？”

先写一个追问，例如“当前有效是指快照仍占正式名额，还是曾经提交成功？”本模拟的确认回复：

- [data-status.csv](data-status.csv) 是截至模拟 **2026-10-07 18:00** 的四行状态快照。
- accepted 为当前正式报名；cancelled 和 waitlist 都不占正式名额。本题当前有效人数应来自本窗口的同一批成功提交者，再关联快照，不纳入其他窗口的人。
- 新指标是 **当前有效人数 / 原来源的可识别访客人数**。它描述窗口内提交者截至快照的状态，不是另一个提交事件率。
- 旧提交指标保留，不能因为某人已取消就删去过去 submit_success 的事实。

规范化两边 ID 后关联，检查每个提交者都有一个快照状态且不重复。缺状态或冲突状态需要标记待确认，不能默认为 accepted。本次快照覆盖提交者；真实数据需自行复核完整性。

## 35–40 分钟：复核与交接

写给组织者的小结，最多六行也可以：

1. 文件、窗口和快照时间；纳入范围与清洗日志位置。
2. V1 的提交事实，引用分子/分母。
3. V2 的当前有效事实，解释旧提交为什么仍保留。
4. 至少一个质量局限和一个业务/因果局限。
5. 下一步要补的数据及它能回答的具体问题，例如取消原因、同口径后续窗口、未识别访客问题。
6. 未完成项目和接手者下一步怎样复核。

检查合计人数、ID 集合、快照覆盖以及有效人数未超活动 20 名。核对后才写“本轮结果可复查”；没完成就交接部分证据，不补造数字。

自己尝试后再看 [参考与复核](data-reference.md)。它含计算答案和解释示例，建议措辞不是唯一答案。

## 40–45 分钟：体验记录

把最后 5 分钟留给页面的通用体验记录。回看定义问题、找脏数据、算数字、改业务口径、向别人解释五段：在哪一段投入？哪一步卡住？得到方法帮助后是否还想继续？完成程度、熟悉程度和兴趣分别记录，不由一次计算推断职业适合度。

## 可选 +20 分钟：Python 复现（主轮之后）

有现成 Python 时，用标准库 `csv`、`datetime`、`collections` 自己写一个小脚本：

1. 读取原始 CSV；按窗口、测试标记、空 ID 与重复 event_id 记录排除行及理由；规范化 ID。
2. 每来源每事件维护 ID 集合，检查嵌套关系；输出人数和带分子分母的比例。
3. 关联状态快照，输出当前 accepted 和旧 submit_success 两套指标。
4. 与自己的人工记录核对；在输入副本追加一条已有事件的重复记录，再追加一条窗外 visit，两次重跑后人数应不变。保留实际输出，若不一致指出第一处差异。

不需要 Pandas、数据库、SQL 服务、账号或安装依赖。环境准备时间另记；启动卡住时保存命令/报错/文件位置，不为环境问题抹去已完成的分析。也可把 +20 分钟用来解释一个人工计算差异，不要求强行写完程序。
